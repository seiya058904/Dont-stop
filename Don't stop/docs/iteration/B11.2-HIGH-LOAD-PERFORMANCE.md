## 0. 一句话结论

B11.1 把「冻结后的静态激光每帧重算墙体裁剪」这一处修掉之后，B11.2 回到同一条测量链上，
把剩下四处**可度量的冗余**做掉，并且这一次**先量后改、改完再量**：

1. **敌人子弹的碰撞 mask 里多带了 layer 1**，于是每发子弹都要给「当时活着的每一只怪 + 玩家」
   各加一条碰撞豁免，才能在效果上等价于「只撞墙」——把 mask 收成只留墙（32），
   豁免整条扇出随之消失；
2. **`FogPierce` 每推一条线都要重新扫一遍世界根节点的所有子节点**，一条线推两次就等于扫两次
   （实测 1.97 次扫描/线），把解析过的画布缓存起来；
3. **`BaseMonster` 每帧对每个角色都做一次「状态字典」遍历**，而实测 **100% 的遍历都是空字典**，
   只为构造一个空 `Array`；加一个 `is_empty()` 守卫；
4. **`HostileZone` 里已经冻结的活跃脚印仍在按物理帧重绘**（`elapsed >= warning-0.15`
   一旦成立就永远成立），停掉对「输入没变、重画结果必然相同」的重复重绘，
   并把它的 Fog 镜像从 `_draw()` 挪进 `step()`，使「信息」不再绑定在「重绘节奏」上。

四项都**不改变玩法**，并且本轮的**每一项都用真实运行时的回归测试**去证明它没改变玩法，
而不是用静态审计去论证——上一轮 `MapNpc.tscn` / `RewardNpc.tscn` 的教训（见 §3.1）说明
「只看 layer 表」是会漏的。

测量侧本轮额外做了三件事，都是为了不让结论跑在数据前面：

* **噪声底**：同一份 BEFORE 构建跑两轮（同源码、同种子、同机器、同窗口），
  用两轮之间的差异量出「同一构建也会有的波动」。**低于 3 倍噪声底的差异不叫结论**（§5）。
* **视觉隔离 A/B**：把「纯视觉产物」逐个关掉再跑同一负载剖面，让「画面忙」这件事
  能按名字分摊成本，而不是靠猜（§6）。
* **像素级视觉验收**：把重绘闸门与镜像挪位这两处改动**在真实渲染帧上读像素**
  （§3.4），因为「0 次重绘请求」只说明没重画，不说明画面上还有东西。

## 2. 做的四项优化（按贡献排序）

### 2.1 敌人子弹：mask 从「layer 1 + layer 32」收成「只留墙」

`game/monster/EnemyShot.gd` 是 `CharacterBody2D`，用 `move_and_collide(velocity*delta)`
决定自己会不会被挡住。旧写法：

```gdscript
collision_mask = 2147483649                                    # bit 1 (玩家+怪物共享层) + bit 32 (墙)
add_collision_exception_with(Utils.player)                      # 再把玩家摘出去
for actor in get_tree().get_nodes_in_group("monsters"):
    add_collision_exception_with(actor)                         # 再给当时活着的每只怪摘出去
```

也就是说：**mask 里带上 layer 1 之后，再用 N+1 条豁免把它抵消掉**，效果才是「只撞墙」。
实测最重剖面下**每发子弹 83 条豁免**、45 s 内 26,846 次物理服务器配对插入，
而且全部集中在开火那一刻成串到达——正好是用户报的「一开火就顿」的形态。

新写法只保留 `collision_mask = 2147483648`。

**伴随修复（必须有，否则这是真的玩法改动）**：`MapNpc.tscn` 与 `RewardNpc.tscn` 的
`StaticBody2D` **没有写 `collision_layer`**，因此落在隐式默认层 **1**。旧 mask 会让子弹停在 NPC 身上，
新 mask 会让子弹穿过去——**这是可见的游戏差异**。两个场景现在显式发布 `2147483649`
（与城镇建筑板完全相同的值）。这个坑是被 `B11ShotLayer` 的 A 段**跑出来的**，不是审出来的（§3.1）。

### 2.2 `FogPierce`：缓存解析好的画布

`push_line()` 每条逻辑线要推 **2** 个条目（车道本身 + 装饰用亮芯），而每次推送都会
`get_children()` 扫一遍世界根节点来重新找那个画布 —— 于是「一条线 = 两次全子节点扫描」。
实测最重剖面 **1.98 次扫描/线**（条目数 1.97 条/线），即几乎每条线的两次推送都在重扫。
改为把解析结果缓存在 `static var`，并且**三个条件**共同决定它还能不能用：

```gdscript
static func _usable(layer) -> bool:
	return is_instance_valid(layer) and layer.is_inside_tree() and not layer.is_queued_for_deletion()
```

三个条件缺一不可，理由写在 §3.2。`_exit_tree()` 里清缓存，是唯一能覆盖
`queue_free()` / `remove_child()` / 整棵树拆除（回营地、下一关、退出）的位置。

### 2.3 `BaseMonster`：空状态字典不必每帧遍历

```gdscript
for source in slows.keys():      # Dictionary.keys() 每次都新建一个 Array
```

这段对**每个角色、每一帧**都跑，无论它身上有没有状态。实测量到的最重剖面上
**100% 的遍历都是空的**，也就是每秒约 9,800 次纯为空数组而做的分配。
守卫用的就是循环自己在第一次迭代会求值的同一个谓词，所以**哪些状态跳、按什么顺序、跳多久完全不变**。

### 2.4 `HostileZone`：冻结脚印停重绘 + 镜像挪进 `step()`

旧重绘闸门：

```gdscript
if visual_clock <= 0 or active != previous_active or elapsed >= warning-0.15:
	queue_redraw()
```

`elapsed >= warning-0.15` 在**开火那一瞬间起就永远成立**，所以一个不再转向的活跃脚印
会在它整个活跃窗口里**按物理帧重绘**，而它的画面此刻是冻结输入的纯函数
（`progress` 被夹到 1、`active` 覆盖两套配色、几何缓存按不会变的值索引）。
这与 B11.1 已经修过的「永久为真」缺陷是同一个形状。

新闸门把「冻结」显式写出来：

```gdscript
var frozen: bool = active and not sweeping and full_detail == previous_detail and global_position == last_draw_origin
if not frozen and (visual_clock <= 0 or active != previous_active or elapsed >= warning-0.15):
	queue_redraw()
```

**镜像同时挪位**，这一点单独解释：`FogPierceCanvas` 只在「本帧有条目到达」时才重绘，
而它的 `_draw()` 是**用它刚刚清空的那份列表重新提交一遍绘制命令**。
真实 Hell 回合里 `EnemyShot` 每个物理帧都会推条目，所以画布即使在本区自己没重绘的帧上
也会被迫重绘——**那些帧上新缓冲区里就没有这条镜像**。
所以镜像必须属于「物理 tick」而不是「重绘节奏」；留在 `_draw()` 里的话，
一个被停掉重绘的冻结车道会每隔一帧丢一次镜像。见 §3.3 与 §3.4。

#### 3.1.1 这次改动唯一的行为差异，是被**量**出来的，不是被论证出来的

新 mask 与旧 mask **不等价的那一处**是：旧代码的豁免只覆盖「子弹生成那一刻已经存在的怪」，
**之后才 spawn 的怪不在豁免里，于是旧 mask 真的会把子弹停在这种怪身上**——
旧行为依赖 spawn 顺序。`B11ShotLayer` 的 K 段用产品的弹丸节点把旧配置**重建出来**，
让同一只怪、同一位置、同一时刻分别面对旧配置与新配置，把差异变成一个可引用的数对：

* 旧配置（`mask = 32|1`，不给这只怪豁免）：**子弹被它挡下**；
* 出货配置：**同一只怪挡不住同一发子弹**。

这条差异的可见性、以及它为什么不算玩法改动，写在 §7 与 §11。

### 3.2 确认点 2 —— `FogPierce` 缓存生命周期

`tests/B11FogCache.tscn`：**30 checks / 0 fail**。它对着真实生命周期事件测，而不是对着 mock：

| # | 事件 | 断言 |
|---|---|---|
| 1 | 无雾 | 没有画布存在，`instance()` 也这么说 |
| 2 | Hell 战斗 | 画布出现，并且**被复用**：重复推送新增 0 次扫描 |
| 3 | `queue_free()` | 被判处死的画布**在同一帧内绝不会被交还**——这正是 `is_instance_valid()` 单独使用会漏掉的窗口（`queue_free()` 是延迟的），由 `is_queued_for_deletion()` 补上 |
| 4 | 跨帧之后 | 已释放的画布消失，`instance()` 返回 null 而不是悬垂引用 |
| 5 | 新回合 | 拿到**新**画布（按 instance id 比对） |
| 6 | 回营地 | 画布自行退休，`_exit_tree()` 清掉缓存，**没有任何引用存活** |
| 7 | 再进 Hell | 重新找到一张全新画布，说明什么都没被记住 |
| 8 | 立即 `free()` | 单独演练 `is_instance_valid` 这一条臂 |
| 9 | 算术 | 画布排空的条目数 == 被推送的条目数，所以 §3.3 据以判定的推送量就是被真正绘制的量 |

另外，B11ZoneVisual 的 M1 段（§3.4）在**每个物理 tick 上**验证镜像被重新提出，
且 M2 段是在「本区自己的 canvas item 被隐藏」的前提下做的——
`visible = false` 意味着这个 zone 的 `_draw()` **一次都不会跑**，
所以此时还能到达 Fog 层的任何东西，**可证明来自 `step()` 而不是 `_draw()`**。

### 3.3 确认点 3 —— Fog push 有没有翻倍、有没有吃掉重绘收益

这是本轮唯一一个「可能把优化做坏」的地方，所以单独列表判定。
口径有四层，缺一层都不能下结论：

1. **push 速率**：`fog_push_lines / s`（逻辑线）；
2. **条目速率**：`fog_entries_appended / s`（每条线 2 条目，所以这个数才是成本量级）；
3. **接受 vs 丢弃**：`fog_entries_dropped` 与丢弃占比——丢弃上升就是「涂不满」的前兆；
4. **Fog CPU**：`fog_draw_usec`（B11.2 新装的计数器，此前只有推断没有读数）。

以及一个必须一起看的口径：**分区**。BEFORE 的推送发生在 `HostileZone._draw()` 里，
AFTER 挪到了 `step()`，所以**只比 `zone_draw_usec` 会偏袒 AFTER、只比 `zone_step_usec` 会偏袒 BEFORE**；
两个分区相加才是同一件事。

还有一处**探针口径差异**必须先讲清楚，否则下表会被误读：AFTER 的 `fog_push_lines`
同时统计 `push_line` **与** `push_circle`（BEFORE 侧只统计 `push_line`）。
这处差异经实测**不影响本节的判定**，依据是两侧的 `pushes / lines` 都稳定在 ≈1.98
（BEFORE r1 1.9803 / r2 1.9758，AFTER r1 1.9824 / r2 1.9815）：若圆占了可观比例，
这个比值会被拉离 2，而四组数据落在同一处，说明该剖面里圆对推送量的贡献接近 0。
更关键的是，同口径的 `fog_pushes`（两侧都按「每一条目一次」计）给出**同样的 +23%**，
所以下面的结论不是被这处口径差异撑起来的。

### 3.4 确认点 4 —— 视觉保真：先机器判据，再像素判据

重绘闸门和镜像挪位都是**关于玩家看到什么**的主张，而「0 次重绘请求」只能说明没重画，
不能说明画面上还有东西。所以分成两半：

**机器半边**（`tests/B11ZoneClip` 的重绘契约段，headless 也跑）：
冻结的不转向车道 **8 帧内 0 次重绘请求**；转向车道 **5 帧内 ≥4 次**。

**像素半边**（`tests/B11ZoneVisual`，真实渲染帧读数）：

| 段 | 你要确认的 | 怎么读 |

M 段的做法值得单独说，因为它是「镜像隔帧消失」这个现象的直读：

* 本区自己的 canvas item 全程 `visible = false`，所以画面上唯一的来源就是镜像；
* **对手方生产者每 tick 强制一次**：真实回合里 `EnemyShot` 每个物理帧都推条目，
  正是它让画布在「本区没重绘的帧」上也被迫重绘——**没有这个对手方，这个读数就复现不出它要查的故障**；
* 对照是**环境中立**的：只把 `pierce` 关掉，雾、光照、地形、车道自身的隐藏动画全部不变
  （若用「关掉雾」当对照，背景一起变了，什么也证明不了）；
* 判据是**逐帧**的：镜像期的**最弱一帧**必须**强于**对照组**最强的一帧**——
  隔帧闪烁恰好会把最弱一帧压到对照组水平，从而在这里失败。

再加上 M1（每个物理 tick 都重新提出，且从未被上限拒绝）——**「每 tick 都推」+「每帧都在屏上」
合起来才是「不会隔帧消失」的证明**。

## 4. 一个必须单独讲的发现：观测开关曾经改了出货行为

这一条不是优化，是**缺陷**，而且是本轮最值得写进文档的一条。

为了做 §6 的视觉隔离实验，我给 `CombatTelegraph.paint()` 加了一个测试专用开关
`iso_td_decor`，写法是：

```gdscript
var decor: bool = detail and not B11Probe.iso_td_decor
```

然后把**六处原本无条件绘制**的装饰笔触改成 `if decor:`。
问题在于 `detail` 是**调用方传进来的降载标志**
（`full_detail = budget_live <= DETAIL_BUDGET(32)`，即场上脚印数），
于是「关掉一个观测开关」这件事，**顺带给六处笔触加上了『并且只在低负载下才画』**：

* 场上脚印 **>32** 时，charge 箭头、cone 瞄准短线与 root 波形、sweep 预览、
  summon 芽 / poison 抖动 / detonate 闪烁 / 兜底 marks **全部不再绘制**。

这直接违反了 **baseline 自己写下的承诺**：
「Under load omit only the redundant origin halo. Footprints, contrast edges, timing rings,
directional arrows and the summon symbol always remain.」
也违反了本轮硬约束「telegraph 可读性不得下降」。

**怎么发现的**：把 baseline 里 `detail` 这个变量**逐处 grep**，发现 baseline 整个文件
**只用过它一次**（原点光晕 `if detail or kind == "summon"`），其余装饰笔触全部无条件。
新代码把它从 1 处变成了 7 处。

**修法（两层，缺一不可）**：

```gdscript
var decor: bool = not B11Probe.iso_td_decor           # baseline 一直画的那批笔触
var detail_ink: bool = detail and decor                # baseline 本来就用 detail 把关的那一处
```

这样 `iso` 关闭时**出货路径与 baseline 逐分支等价**，`iso` 打开时仍能一次性静音装饰层。

**通用教训**：给产品加「测量/隔离开关」时，必须证明**开关关闭 ⇒ 与 baseline 逐分支等价**，
而不是「看起来只多了一个条件」。做法是对每个被改的条件，
grep 出 baseline 里**该变量的全部出现点**逐个核对。
另外：**改了源码就必须重导出并重测**——不能拿旧构建的数字当交付物的数字。
本轮就是这么做的：`index.pck` 重新导出（identity 变化），AFTER 全套重跑。

**对 BEFORE 侧的影响，如实说明**：BEFORE 构建是「测量参照物」不是交付物，
它与 AFTER 在 `decor` 这一处实现版本可能不同。但该分支只在 `detail == false`
（即 >32 个 live footprint）时才有差异，而**所有核心场景实测 `zones_peak ≤ 30`**
（A 16 / B 16 / C 22–26 / D 29–30，远低于 32），即**从未进入该分支**。
因此该差异对两侧数字都不产生影响；AFTER 侧的构建则与交付分支的源码一致。

## 11. 人类可见的取舍（Human-visible compromises）

按重要性排序，**包括对我们不利的部分**：

1. **姿态：Fog 镜像的刷新率上升了。** 为了让「停掉重绘」不至于每隔一帧丢一次镜像，
   镜像从「跟着重绘走」改成「每个物理 tick 都推」。代价是最重剖面下 Fog 侧推送量上升
   （见 §3.3 表：既不是翻倍，也没有吃掉重绘收益，且**丢弃反而更少**）。
   换来的是：一个被停掉重绘的冻结车道，其镜像**每一帧都在屏上**（§3.4 M 段逐帧读数）。
   这是一次「多花一点 CPU 换掉一个隔帧闪烁」的取舍，并且 CPU 那一侧是量过的。
2. **活跃且「不转向」的脚印会停止重绘，代价是四处装饰性动画随之冻住。**
   停重绘的判据是「输入没变、重画结果必然相同」。这条判据对**契约层**成立：
   `CombatTelegraph.paint()` 第 107 行把进度 `p = clampf(progress,0,1)`，
   活跃期 `p` 恒为 1，`active` 又同时覆盖 `edge` / `fill` 两项调色板，所以轮廓、填充、
   两条倒计时弧、光束本体，全部是「冻结输入」的纯函数——这正是玩家读得出、躲得开的那一层。
   但同一个函数里有**四处装饰笔触**读的是**未截断的原始 `progress`**
   （第 158 行 root 波形、第 178 / 181 行 poison 抖边与孢子、第 185 行 detonate 内闪）；
   活跃期这个值随时间无限增长（`elapsed / warning`），所以 baseline 里它们一直在动，
   停重绘之后会静止。**这是本轮唯一一处「画面上真的变了」的表现层改动**，如实列出。
   为什么仍接受：这四处按 painter 自己的契约属于可省的装饰层（`iso_td_decor` 关掉的正是它们），
   而保住它们就得让活跃脚印继续按物理帧重绘——那正是本轮要停掉的东西。
   取证口径要说清：**测试没有覆盖这一条**（§3.4 的 A 段只断言活跃冻结车道**每帧都有墨**、
   且最弱帧不低于中位数 60%，并不要求墨在动），所以它是**读代码得出的结论，不是量出来的**。
3. **一个真实的、量出来的行为差异**：旧构建里「子弹生成之后才 spawn 的怪」会挡下子弹，
   新构建不会（§3.1.1 的 K 段把两侧都跑了出来）。方向上它只会让弹幕**更难被中途吃掉**，
   不会让玩家更容易。之所以接受：旧行为依赖 spawn 顺序、并不自洽，
   而维持它需要把那条 O(N) 豁免扇出留下，那正是本轮的优化对象。
   如果需要「子弹可被怪挡下」，正确的做法是显式设计（比如给怪加一层专门的
   `shot_blocker` 层），而不是靠豁免快照的时序副作用——本轮没有这么做，因为那是玩法改动，不在 B11.2 范围。
4. **`MapNpc.tscn` / `RewardNpc.tscn` 的层值被显式写出。** 这两个场景原本靠
   「不写就是 layer 1」的隐式默认值。改动后行为与之前**完全一致**（NPC 仍然挡子弹），
   但这是一处**必须随 mask 优化一起发布**的伴随改动：只改 mask 不改它，
   就会出现「子弹穿过 NPC」的真实可见变化。
5. **`iso_*` 六个开关随构建发布。** 它们默认全关、只在 `?stress=1` 的测试路径上才可能被点亮，
   正常玩家不可能触达（`web/loader.html` 里只在 `params.has('stress')` 分支内追加参数）。
   代价是产品源码里多了六个测试专用分支；收益是 §6 那张「哪个视觉产物花多少」的表是量出来的。
6. **没有降低任何难度。** 第 39 关敌人上限仍是 84，怪物数 / 攻击频率 / 精英 / 机制 /
   关卡长度 / Boss 内容一项未动；telegraph 的信息量只增不减（§4 修掉的那一处是**原本就不该发生**的减少）。

## 12. 已知未决项（如实记录）

1. **用户报告的「卡顿」在本机上仍无法复现为帧时间尖峰信号**（B11.1 §4 的结论不变）：
   本机 60 Hz vsync 锁帧 + 每次回合开始都有一个 ~150 ms 的起步顿挫，
   后者吃掉大部分尖峰计数。所以本轮的主判据是**与 vsync 无关的**物理微秒计数器，
   帧时间数字只作为「有没有变坏」的护栏。
2. **`fog_draw_usec` 等四个 Fog 侧计数器只存在于 AFTER 构建**（B11.1 的探针里没有它们），
   所以 Fog CPU 的 BEFORE 侧没有同口径读数。BEFORE 侧的 Fog 成本**包含在
   `zone_draw_usec` 里**（推送发生在 `_draw()`），因此 §3.3 用「draw + step 合计」做同口径比较。
3. **BEFORE 构建的 `decor` 实现版本可能与 AFTER 不同**（§4 末段），
   影响范围限定在 `detail == false`（>32 live footprint）这一条实测从未进入的分支。
4. **`docs/iteration/STATUS.md` 里对 CI 的描述仍是旧的**（停在 4 个门禁那一版）。
   修它需要再往 `main` 推一次提交，而按交付纪律「部署并核对指纹之后不应再推 `main`」，
   所以留作下一轮入口。
5. **`shot_exceptions` 的 AFTER 侧 0 是「计数点不存在」，不是「量到 0」。**
   BEFORE 构建里那条豁免扇出带着计数点，因此测到 82.8 次豁免/发、708.8 次/s；
   AFTER 把豁免代码整段删除，**计数点随之一起消失**，于是它恒为 0。
   所以这个「−100%」的准确含义是「那段代码已经不在树里」——
   由 diff 与 `tests/B11ShotLayer` 的 B 段（出货 mask 只留墙，bit 1 不在其中）直接断言，
   而不是一次同口径的前后测量。§5 表里它被判为 ATTRIBUTABLE，指的是
   「被删掉的代码不再运行」这件事**确定无疑**；不要读成「性能提升了 100%」。
   相应地，`B11ShotLayer` 的 F 段「`shot_exceptions` 不变」在本树上是个**恒真断言**
   （没有任何代码路径能再把它改掉），它证明的是「没有新增豁免」这一意图，不是数值对比。
6. **`HostileZone.step()` 的注释把 `progress` 的截断说窄了**（配合 §11 第 2 条）。
   注释写「`progress` is clamped to 1」：这对**契约层**成立（`paint()` 内部
   `p = clampf(progress,0,1)`），但四处装饰笔触读的是**原始** `progress`，并不截断。
   这条只影响注释的准确性，不影响出货行为；**本轮不改**——改源码会让 `.pck` 字节变化，
   从而让「测的就是浏览器实际加载的这一份」这条证据链断掉，应与下一次测量一起做。
7. **本轮未合并、未部署、未打标签**：交付状态是
   `WEB_DEPLOYED_FOR_HUMAN_REVIEW=false` / `HUMAN_ACCEPTED=false` / `WEB_HUMAN_ACCEPTED=false`，
   等待人工验收。
