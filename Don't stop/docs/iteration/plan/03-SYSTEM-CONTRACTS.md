# 03 最小工程契约：只为可玩升级服务

## 1. 建立独立Godot副本，不碰冻结源

工作区可能位于 `D:\xia zai\AI project\8.30 Backup game\`。这是用户给出的本地路径线索，不是云端已验证目录。先从当前cwd、根README和已有启动器定位，不扫描无关硬盘。

三个只读目录：`TowDownGame/`、`Godot-GameTemplate/`、`Barren-Game/`。完整复制原型的功能源码、场景、资源、导入声明和项目设置为 `TowDownGame-Iteration/`，不继承原仓库`.git`，不需要复制可再生`.godot`缓存和旧导出大二进制。不得遗漏隐藏的必要源文件或未跟踪但实际使用的素材；生成复制清单。

“独立项目”指独立Godot根目录和存档，不强制再增加一个嵌套Git仓库。默认让迭代副本作为外层 `game-prototype-lab` 的普通受跟踪目录，原三个目录的本地独立Git元数据保持不动。这能避免外层只提交一个gitlink而云端看不到源码。

如果副本已经存在，先读状态与进度，绝不覆盖重建。记录冻结源的工作树状态和源文件hash；后续重新导入和运行基线比较用临时副本，避免编辑器自动升级/生成UID改到只读源。

根目录只允许为纳入迭代副本而做必要的README、忽略规则和资源追踪规则调整；游戏代码只进入副本。工具、临时试玩比较副本、下载和重型证据留在现有 `archive/workspace-support/`，不全局安装。

## 2. 遭遇状态明确，但不重写成大型状态机框架

至少区分：`CAMP`、`PREPARING`、`COMBAT`、`RESOLVING`、`DEAD`。暂停是独立的原因集合/栈，不和战斗状态混为一谈。

进入战斗只能通过一个入口：校验已装备可用枪→锁传送入口→建立本次遭遇代次→初始化刷怪和计时→进入COMBAT。结算将代次标记已完成，停止刷怪、伤害和敌方攻击，结算一次，然后回营地。定义同帧优先规则：若倒计时完成前玩家已判定死亡，走死亡流程；如果先完成有效胜利锁，后到的旧伤害不得再杀死营地玩家。测试其确定性。

暂停时停止射击、伤害tick、敌人AI、刷怪、战斗倒计时和移动；菜单、提示和恢复入口仍然可操作。关闭一层UI只释放该层暂停理由，不擅自解除其他理由。失焦默认暂停单人战斗；恢复时清除旧的按住开火状态，避免回到窗口自动打一枪。

不要借助“把局部delta写成0”宣称暂停整个物理系统。Godot暂停和process mode的实际契约查官方文档[S23]并用本地版本验证。

## 3. 统一交易入口，保留原UI外观风格

建议用一个小的购买服务函数返回结构化结果；不必建设商城框架。

```text
try_purchase(kind, definition_id, payment_currency, expected_rank?)
→ { success, reason, charged_currency, charged_amount,
    obtained_instance_id?, old_rank?, new_rank?, effective_stat_delta? }
```

`kind` 明确武器/配件/天赋/补给；ID来自注册表，不从显示文本猜测。步骤是验证商品→验证余额/上限/归属→准备可应用变更→一次性应用与扣款→发布状态变更和反馈。异步失败时恢复旧状态，不产生“扣了钱但没得到”的半事务。

重复拥有同一种枪默认不重复购买；配件允许多实例，每次购买形成唯一实例；天赋按等级购买。错误和满级状态不扣款、不播成功音。购买按钮短时防重复，服务端逻辑本身也要检查，不能仅靠禁用按钮。

所有扣费、所有权和等级变更只从这条入口发生；原枪店、天赋页和快捷购买都复用它。

## 4. 有效属性从基础值重算

保留现有枪械场景作为基础定义，提取不可变基础值；将附加属性区分为：固定加法、百分比加法、独立乘法、机制flag。确定并记录计算顺序，例如：

```text
effective = clamp((base + flat_total) * (1 + additive_percent_total)
                  * multiplicative_total, legal_min, legal_max)
```

此公式是默认的统一契约，不用于偷偷改变现有枪的基础强度。不同单位必须明确：每秒发数、秒/次、每发弹丸数、每tick伤害、像素/秒、概率0–1。旧参数命名含糊时建立适配，不凭变量名推断真实单位。

卸装回到同一基础值；重复刷新不漂移；切枪不污染别的枪；两把枪共享资源时不共享实例可变状态。弹匣变化保留当前已装弹、不凭空补满；缩小容量时多余子弹退回备弹或采用显式记录的保守策略。

装填时间和射击间隔必须有正下限，暴击概率和减伤有合法范围，元素tick有最小间隔。新武器、配件、天赋的最大组合不能产生0秒timer、除零、NaN或无界循环。

HUD/详情/预览读取同一有效属性快照，不能各算一遍。需要写测试检查基础、单件、组合、移除、重装20次和保存恢复。

## 5. 伤害事件、射弹与派生效果

建立轻量伤害载荷，不为激光命中临时造一个无归属的场景对象。建议字段：来源实体/武器ID、遭遇代次、攻击序号、伤害单位、伤害类型、暴击结果、冲量、标签、派生深度。避免建立一套与现有战斗平行的伤害系统；逐步让既有枪走同一结算入口。

伤害、暴击、天赋触发、受击反馈、死亡奖励分清职责。普通弹、光束、范围爆炸、链电、持续状态都必须测试同一批增益的适用范围；UI不能承诺不实际生效的加成。

光束按固定伤害tick而非渲染帧扣血；高速实体弹在物理更新中验证连续运动碰撞。一次命中后从正确的新位置处理剩余行程，穿透/弹跳需有限循环和微小脱离量，避免0距离自碰撞。用确定性测试覆盖薄墙和同帧多个敌人。

派生效果默认最多2层；源头标签控制哪些事件能再触发。爆炸触发的电弧、电弧触发的爆炸不能互相无穷生成。每个攻击对同一目标的命中次数、tick间隔、弹跳/贯穿数和生命周期均有上限。

敌人死亡先设置幂等标记，再掉落/经验/击杀触发；死亡目标不再作为新链目标。使用可复现随机种子做测试，不在正常运行中为强制爽感偷偷设胜者或动态改命中。

## 6. 生命周期与资源预算

遭遇内子弹、残骸、伤害数字、掉落、连锁任务和临时音频归属清楚。回营地、重开或换场景时清理本次遭遇域；不把无限多效果挂到全局root而没有回收。

引入池仅针对已测出的高频对象。回收必须清碰撞例外、已命中目标集合、状态层数、剩余寿命、音频/粒子、Tween、信号与旧代次；重复回收必须安全。不要先池化全项目再制作内容。

可视特效预算可以降低装饰粒子、合并数字、减少残骸；绝不能因画质降低而丢伤害、删关键敌弹、缩小攻击判定或改变随机结果。关键危险预警优先于我方装饰爆炸。

## 7. 稳定ID和最小保存

武器定义ID/配件定义ID/天赋ID稳定；实例ID只表示同类型的具体一份物品。运行时Time生成的节点ID不能当跨存档内容主键。保留现有ID映射，新增项使用无冲突命名；不要改旧ID后让存档悄悄错物品。

副本采用独立应用名或明确的 `user://` 自定义目录；不能读写原版 `Don't Stop` 的配置/进度。Godot用户数据位置参见[S24]。

只保存必要数据：schema_version、build_profile、钱包、拥有武器ID、配件实例及装配映射、天赋等级、下一关/已选试玩关、设置。存档不序列化Node对象或任意脚本。保存前校验，临时文件写入成功后替换；坏档先保留备份并提供显式新开，不用默认值自动覆盖原文。

在营地购买/装配与通关回营地后保存。中途关闭后从上次营地快照恢复，不复原一半结算的战斗。测试加载不重复发9999、不重复应用增益、不跳过未完成关卡。
